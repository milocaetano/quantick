# Goal — map every supported UI behaviour to a capability or a recorded exclusion

Map every supported UI behaviour to a named control-plane capability or to a
recorded, legitimate exclusion, generated from code with a drift fixture, so
rubric criterion AP1 earns its next point.

Why it matters: `CLAUDE.md`'s *Operable without a hand* says no capability
ships reachable by mouse alone. The control plane answered half of that — 38
capabilities in a generated, guarded inventory — and nothing answered the other
half. Nobody could say which of the behaviours a trader reaches an operator
cannot, so a gap and a deliberate refusal looked the same.

**Tier:** `medium`. A campaign child of #367 (key Q5) at the tier the parent
assigned: a new module, a new generated document and a new guard, with
`arch-review` at full shape pass, `code-review` at `low`, `ai-review`
completion and a `delivery-review` completeness pass inline.

**Campaign:** child of https://github.com/milocaetano/quantick/issues/367 (Q5).
Base `origin/campaign/lean-a-plus`; PR base exactly `campaign/lean-a-plus`.
Task issue: https://github.com/milocaetano/quantick/issues/381.

## Request ledger

- **R1** — Enumerate every supported user behaviour reachable from the UI
  (menus, hotkeys, toolbar, tool rail, context menus, dialogs) and map each to
  a named capability in the versioned registry or to a recorded, legitimate
  exclusion. *(issue #381 Scope, bullet 1)*
- **R2** — Generate the matrix from code where possible, persist it as a
  generated artifact regenerated by a documented command. *(issue #381 Scope,
  bullet 2; A1)*
- **R3** — Add a drift fixture that fails when a new UI behaviour is registered
  without a row, and when a row names a capability the inventory does not have.
  *(issue #381 A2; D2)*
- **R4** — Coverage is 100% of *registered* behaviours; gestures no registry
  stands behind are either registered or listed in a short appendix with the
  reason and the count. *(D3)*
- **R5** — Enabling a capability for an excluded behaviour is a product and
  authority decision: record each candidate as a `pending_capability` row, never
  enable by default, change no permission, descriptor or profile. *(issue #381
  Scope bullet 3; D4)*
- **R6** — The exclusion classes are closed: `authority`, `ui_only_by_decision`,
  `pending_capability`, each citing its descriptor, decision or issue. *(D1)*
- **R7** — No per-frame cost: the matrix is built at test and generation time
  only, and the runtime paths are unchanged. *(D5)*
- **R8** — The assessor's observable condition is met and AP1 is reassessed at
  the PR head. *(issue #381 A3)*
- **R9** — Delivered through a PR whose base is exactly `campaign/lean-a-plus`.
  *(issue #381 A4)*

## Decisions

The coordinator answered step 3's questions before work started.

- **D1** — Generated from code, not hand-kept. Every UI behaviour registered in
  a registry the app already has gets a row with behaviour id, reach, and
  either a capability id or a closed exclusion class with a reason. Persisted as
  `docs/control-plane/ui-behaviour-matrix.md`, regenerated by a documented
  command, the mechanism the capability inventory uses.
- **D2** — The drift fixture: the guard fails when a UI behaviour is registered
  with no matrix row, and when a row names a capability the inventory lacks.
  Proven with a fixture registration and the failing output recorded in the PR
  body.
- **D3** — Coverage means 100% of *registered* behaviours. Unregistered gestures
  that are user-facing actions are carried in the table; the rest are listed as
  not-a-behaviour with the reason and the count.
- **D4** — Enabling an excluded behaviour is out of scope: record it as
  `pending_capability`, raise a `human_decision` where one is worth it.
- **D5** — No per-frame path; nothing built at runtime.
- **D6** — Tier `medium`: `arch-review` with `code-review` at `low`, full shape
  pass, `ai-review` completion, `delivery-review` completeness pass inline.
- **D7** — `gh pr ready` once, after reviews, markers and green CI. Never merge,
  never touch main, never use the PowerShell tool for `gh pr`.
- **D8** — The size rule applies; `cargo test -p quantick-guards` green after
  each batch; the context ratchet checked for the new document.

## Assumptions

- **S1** — The behaviour table lives in a new `crates/app/src/operability/`
  module rather than under `crates/app/src/control/`, because a sibling mission
  owns the control production files. Reversible in one move.
- **S2** — Capability identifiers are read from the committed, generated and
  already-guarded `docs/control-plane/capability-inventory.md` rather than by
  building a second `ObserverContract`, because `control`'s submodules are
  private and widening them is an edit to files a sibling owns. *Wanted to ask.*
- **S3** — The `pending_capability` rows all cite one tracking issue rather than
  one issue each, because the matrix is the enumeration and thirty stubs would
  put the list in two places. Issue #401 was opened for it.
- **S4** — The 12 menu entries whose labels the source computes cannot be
  claimed by key, so they are counted instead: a new one changes the count and
  fails the guard.

## Not applicable

- **Hot path** — nothing runs per trade, per depth or per frame; the table is
  `const` data and the guard is test-time. No benchmark owed.
- **User-visible surface** — no surface changes, so `ui-harness`, `visual-qa`
  and `trader-ux-review` do not apply. The one production edit outside the new
  module is a dump subcommand and a visibility widening.
- **Adds a capability** — deliberately not: D4 forbids enabling anything.
- **Engine / determinism** — no engine code touched. The generator is
  deterministic by construction (a `const` slice rendered in its own order),
  which the byte-comparison test guards.
