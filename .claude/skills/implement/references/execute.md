# Goal: validated PR
Read this file and the plan. Follow repo permissions, hooks, `CLAUDE.md` and `CONTRIBUTING.md`.

**Level:** the higher of the plan's `Review:` and this floor: `high` for hooks, guards, auth, orders/trading, concurrency, public contracts or >600 changed lines outside `schemas/`; `low` for non-behavioral docs/config/tests or a local <=150-line change with no contract change; otherwise `medium`. Estimate it before building; raise it when risk or the diff crosses a floor, then do any step it now requires.

**Context cap:** review runs in the code-review interface's agents, checks and CI in background `sh tools/verify.sh`. Past ~50 build or repair tool calls since the last commit or handoff, commit a green seam (WIP if needed), append done/next to the plan and continue in a fresh `Agent` given plan path, worktree, SHA, level and next action, never the conversation; it returns SHA and check results.

1. **Isolate:** verify the pinned base, target, remote and CI. Reuse an isolated task worktree only when its ownership, branch, base and status are right; otherwise create one from the pinned base. Target not `main`: `echo "$(git branch --show-current) origin/<target> none none" > "$(git rev-parse --absolute-git-dir)/mission-base"`. Else update by `sh tools/merge_main.sh`. Preserve unrelated changes. Run tools with its explicit working directory. Note `cargo run -q -p quantick-guards -- --report` crate.lines.app and .total (production, tests excluded) at base. Declare the tier there: `echo "$(git branch --show-current) implement" > "$(git rev-parse --absolute-git-dir)/mission-tier"`.
2. **Build:** first find the owning module, its types, contracts and tests; reuse what the dependency graph lets you import, never mirror it, and delete what the change replaces. The owner's command and result types are the wire types; a DTO only where the wire must differ. New state and decisions go in a headless crate outside `crates/app`, with their tests; in `crates/app` a feature adds only a field holding that state on its owner, one-line calls into it, and egui painting and input. When the ui-free ratchet fires, move the cause out; raise only for code touching app-only state. Keep APIs narrow and concrete: no enum for a bool, no struct or parser beside an existing one. Functions <=200 lines. No unrelated restructuring or dependencies. Named constants for policy, configuration for varying values; no secrets. Make the smallest complete, testable change; Size never cuts validation, refusals, error paths, edge cases or module, port, wire, contract and SAFETY docs. A new module opens with at least one //! line; a port, hub or crate root also states its contract and owner. Other comments state only a why or contract identifiers cannot.
3. **Agent operation:** expose new user workflows through the existing API/CLI/MCP contract besides the UI: discoverable calls, validated inputs, structured results and errors, state inspection, bounded outputs, progress for long work. Enforce authorization and side effects in code; retries never repeat non-idempotent actions. A fix or restyle adds no capability, call or schema beyond a refusal code; a missing one is a Decisions line.
4. **Checks:** test each decision once, in its owner crate; cases differing only in data are rows of one table test whose messages name the row, on the module's setup helper, never a copy; distinct decisions or action sequences stay separate tests; other crates add a test only for wiring nothing else covers (port facts, egui input, frame order, surfaces agreeing), one per path, never the owner's result. Reproduce an app-seen bug at the layer that decided wrong; a fix tests only what it changed; a behavior-free move adds no tests and keeps those it carries. An app test the change edits that asserts an owner's result moves to its owner; one goes only once the PR names owner tests on real types covering each case; preserve behavior coverage, not assertion counts. Tests build owner types through the owner's fixture, never a full struct literal or copied setup. Test refusals, failures and boundaries; merging tests keeps every such case; golden fixtures stay files; every test is deterministic. Measure only hot touched paths against one baseline. Apply the [delivery contract](../../../../docs/workflow/delivery.md#validation-follows-changed-inputs); run required checks on a stable tree. Reuse a passing result only while its inputs, toolchain and environment hold; a new agent never reruns one merely to own it. No production actions or live trades.
5. **Independent review:** commit the scoped work, then get a review from someone other than the implementer through the host's code-review interface (Codex: native review or direct inspection), the level as first argument where accepted, scoped to `git diff origin/<target>...HEAD -- . ':!schemas'`. The reviewer checks acceptance, check evidence and Size, naming any in-process mirror, type restating another's fields, copied test setup, cases one table could hold, test or type added to moved code, re-tested owner result, glue or name-restating comment to delete and any check, error path or contract doc cut for Size, running missing or doubtful checks. For any user-visible or agent-facing change, an independent test agent then uses it as a human would (the app via `ui-harness`, else CLI/MCP) on a stable snapshot without chat context, covering applicable authorization, effects and retries; it reports evidence, and a failure blocks.

   The reviewer tags each finding `blocker` (failed acceptance or check, wrong or unsafe behavior, data loss, a broken `CLAUDE.md` rule) or `follow-up`. Code only blockers and deletions it names; every other finding is one Decisions line, and an architecture one (boundary, mirror, misplaced test, missing call, ratchet raise) also links an issue. At most two review rounds, counted in the PR. After the second, confirm fixes with one `low` delta review outside the budget. A follow-up review checks the prior report, the delta and affected findings; changed base/scope or uncertain evidence requires a full current review. Each review brief lists the names above, asks for the tags and ends: `Last line: REVIEW-VERDICT: pass|fail <worktree> <HEAD>; pass = no unresolved blocker.` A hook records `code-review-ok` from it; never write it (Codex: the user runs pr-gate's command). If pr-gate still denies, stop at once with `BLOCKED` and the denial.
6. **PR and delivery:** before first PR creation or actual handoff, read sibling `pr-context.md` once. Push and open one non-draft PR with `--base <target>`, or update the existing one. Never merge, auto-merge or force-push. Verify all required CI on the current remote HEAD and provider merge revision where applicable; pending, failed, cancelled or missing/skipped checks are not green. Finish only with acceptance, independent review, test-agent evidence when applicable, no unresolved blockers and green CI. Report the full PR URL, SHA, review level/reason and test/CI/performance evidence; else a concrete `BLOCKED` cause.
