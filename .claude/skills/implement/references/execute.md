# Goal: validated PR
Read this file and the plan. Keep only relevant requirements, symbols, diffs and check evidence in context. Follow repo permissions and hooks. This goal replaces the repository's mission workflow and its reviews: skip `/mission`, `arch-review`, `ai-review` and `delivery-review`. Write task artifacts in English, preserving code identifiers and required product text.

1. **Isolate:** verify base/target/remote/CI, sibling `pr-context.md`, and access to a test agent and an invocable code-review skill. Create a new branch and worktree from the pinned base (`git worktree add -b`). Preserve pending changes; run tools in the new worktree with an explicit working directory. From it, declare the tier: `echo "$(git branch --show-current) implement" > "$(git rev-parse --absolute-git-dir)/mission-tier"`.
2. **Lean architecture:** before coding, locate the owning module, a relevant existing precedent if available, and affected contracts/tests. Read enough surrounding code to validate the choice; do not scan the whole repository by default. Follow existing conventions and pragmatic **SOLID** (SRP/OCP/LSP/ISP/DIP). Keep related behavior and owned state together. No God Objects/Classes or unrelated catch-all managers/services. Use narrow module APIs, private internals and explicit dependencies; avoid cycles and mutable global state. Keep domain logic independent of UI, transport, storage and LLM providers. UI and agent entrypoints must reuse the same domain operations.

   Prefer concrete implementations. Add abstractions only for current variation, meaningful boundaries or necessary test isolation. Keep required extension/scaling practical. Deliver the smallest complete, independently testable change, including tests; not merely the smallest diff. Refactor only what correct integration requires. No unrelated restructuring or speculative patterns, frameworks, services or dependencies.
   Split by responsibility, not file count or line quotas. Create files for cohesive boundaries, testability or required extension; neither combine unrelated responsibilities nor fragment cohesive code to game limits.
   Code/tests: <=1,500 physical lines/file and <=200/function/method/closure, including comments/blanks. Ceilings, not targets; split earlier when responsibilities require it. New or previously compliant units must stay within limits. For pre-existing violations, allow only safe local changes that do not increase their size or responsibilities; record the debt in the PR. Extract only when necessary or approved. Stricter repository policies/checks still apply; never waive or weaken them to use this exception.
   No hardcoded values: use named module-level constants outside functions/classes, configuration/injection for variable values, and no secrets in code.
   Record material design trade-offs briefly in the PR. Update existing repository documentation when durable architectural rules change; do not duplicate task history or create documents for routine changes.

3. **Agent operability:** expose required agent-facing workflows through existing API/CLI/MCP interfaces, not GUI-only interaction. Provide discoverable, stable contracts, validated inputs, concise structured results, actionable errors and state inspection. Filter or paginate large outputs. For long-running work, expose progress/status and results. Expose useful workflows, not every internal function; add no unnecessary protocol, framework or LLM dependency. Make side effects explicit and enforce authorization in code. Support safe retries; never blindly retry non-idempotent actions.
4. **Performance:** avoid unnecessary allocation, I/O and contention on critical paths. When affected, compare baseline/change under the same scenario; no unauthorized regression or invented measurements.
5. **Test:** add deterministic unit tests for success/errors/boundaries, regression tests for bugs, and integration tests where needed. A test agent distinct from the implementer must execute checks and validate acceptance. For changed agent-facing workflows, give it only the bounded task, published contracts, scoped rules and a stable test checkout: it must execute the workflow and inspect its outcome without hidden chat context. Include authorization, side-effect and retry behavior where applicable. Keep its tested snapshot stable through commit, or retest. Fix and retest. No production actions or live trades.
6. **Review:** commit the scoped changes, then, before any PR, invoke the existing code-review skill through its actual interface with a distinct reviewing agent. Pass the level as its first argument: the plan's `Review:` if set; otherwise `high` for hooks, guards, auth, orders/trading, concurrency, public contracts or >600 changed lines, `low` for docs/config/tests or a local change <=150 lines with no contract change, else `medium`. Record level/reason in one sentence. Use this review to check boundaries, unnecessary complexity and contract changes; no extra architecture agent is required. Fix valid findings without unrelated style rewrites or demands for architectural perfection. Mandatory standards still apply; disputes require evidence and revalidation. Reassess depth if scope/risk changes. Then, from the worktree: `git diff origin/main...HEAD | git hash-object --stdin > "$(git rev-parse --absolute-git-dir)/code-review-ok"`.
7. **PR:** after review, push and open one PR against the intended target; reuse it. Load `pr-context.md` beside this file for the concise shared brief and agent handoffs; do not maintain duplicate evolving state in the plan. No merge, auto-merge or force-push.
8. **Green:** after fixes, rerun affected tests/review, commit/push and verify all required/applicable CI for the **current remote HEAD** (including its provider-generated merge revision where applicable). Pending, cancelled, unexpectedly skipped/missing checks or previous-SHA results are not green. Never weaken tests, checks or protections.
9. **Finish:** success requires acceptance, test-agent validation, review without blockers and green CI at HEAD. Leave the PR open. Report only URL, SHA, review level/reason and test/CI/performance evidence. Missing mandatory capability or an unresolved blocker means `BLOCKED` with cause, evidence and required action. Never impersonate agents or fabricate approval. Human approval remains human.
